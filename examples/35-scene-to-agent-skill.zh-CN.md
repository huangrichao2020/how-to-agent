# 场景到 Agent Skill

实战 agent 架构里，用户意图和工具调用之间应该有一层。

这一层叫工作场景。

很多 agent 会从“用户说了什么”直接跳到“调用什么工具”。简单任务还行，但一到真实业务就容易出事，因为 agent 没有先判断这件事的性质：

- 高频还是低频？
- 输入结构化还是混乱？
- 动作可回滚吗？
- agent 能不能自己做？
- 哪里必须人确认？
- 结果该不该沉淀成 skill？

`hmy1990116/ai-training-methodology` 对我们最有价值的，不只是 AI 培训课程，而是这条模式：

```text
业务场景 -> 原子动作 -> 六维评估 -> skill 类型
```

放到 agent 系统里，就是：

```text
用户场景 -> 原子动作 -> 风险/频率评分 -> 运行时策略
```

## 原子动作

原子动作必须小到能执行、能 review、能回滚：

```text
角色 + 输入 + 动作 + 输出 + 完成条件
```

坏例子：

```text
处理客服。
```

更好的拆法：

```text
读取最新客户消息。
判断问题类型。
查询订单状态。
起草回复。
如果涉及退款或升级，要求人确认。
发送确认后的回复。
```

这对 agent 很重要，因为安全边界通常不在流程标题里，而在小动作里。

## 六维运行时评估

每个原子动作都问六个问题：

| 维度 | 运行时意义 |
|---|---|
| 规则明确性 | agent 是按规则执行，还是主要靠判断？ |
| 执行频率 | 值不值得自动化，还是只值得辅助？ |
| 数据结构化 | 工具能不能稳定解析输入？ |
| 情境可预测性 | 异常情况是否已知？ |
| 错误可承受性 | 做错能不能低成本回滚？ |
| 人机协作必要性 | 是否必须人确认、决策或协商？ |

这会产生清晰路由。

## A/B/C Skill 类型

### A 类：全自动 Skill

适合重复、结构化、低风险工作。

运行策略：

- 自动触发
- 确定性脚本或窄工具
- 监控
- 重试
- 回退
- 简洁汇报

例子：

- 格式转换
- 状态同步
- 日报组装
- 日志健康检查

### B 类：Agent 主导 Skill

适合 agent 能做大部分工作，但关键节点必须人确认的任务。

运行策略：

- 长任务工作台卡片
- 可见计划
- 人话动作
- 审批确认节点
- 回退路径
- 最终证据汇报

例子：

- 改源码并重启
- 起草并发送外部消息
- 部署上线
- 生成业务文档并最终确认

### C 类：认知辅助

适合判断、品味、关系、谈判、战略不确定性占主导的任务。

运行策略：

- 只分析
- 比较选项
- 起草多个方案
- 显示不确定性
- 人决策和执行

例子：

- 战略选择
- 关系分析
- 招聘判断
- 高风险商业谈判

## 对 GA/Hermes 的架构影响

GA 和 Hermes 已经有工具、记忆、skills、渠道、长任务卡片、重启路径和源码管理技能。现在缺的是稳定的场景分类器。

应该补上这条路径：

```text
消息
  -> 场景分类器
  -> 原子动作
  -> 六维评估
  -> A/B/C 运行策略
  -> tool / skill / 人审 / 回退
  -> trace
  -> 晋升候选
```

这能防止两个常见问题：

1. 过度自动化：agent 在应该只建议的地方擅自行动。
2. 自动化不足：agent 反复手做安全、结构化、高频工作。

## 晋升规则

不要把一个有用想法直接晋升成 skill。

只有当这类工作满足这些条件时才晋升：

- 重复出现；
- 操作性强；
- 边界清楚；
- 可验证；
- 不需要保存原始私密日志；
- 作为 skill 召回比每次从记忆重建更省成本。

晋升路径是：

```text
trace -> 重复原子动作 -> A/B/C 类型 -> skill 候选 -> 已验证 skill
```

## 一句话记忆

真正的升级是：

```text
agent 行动前，先分类工作单元；工作流晋升成 skill 前，先证明频率、边界、风险和验收路径。
```

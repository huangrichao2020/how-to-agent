# Agent 架构审计师

这个方法把 how-to-agent 的架构精华压缩成一个可复用审计 skill。它不是为了夸 agent 有多复杂，而是检查这些架构是否真的改变了行为。

## 核心公式

```text
好的 agent 架构 =
  清楚的任务信封
  + 最小有效上下文
  + 稳定运行主链路
  + 可复用 skill/tool/memory
  + 可验证输出
  + 能改变下次行为的沉淀
```

## 审计对象

- Task Envelope：真实目的、边界、风险、验收。
- Context Pack：最小上下文、渐进披露、反堆砌。
- 注意力治理：PromptComposer、RuntimeController、FeedbackLoop。
- Ω-Brain：感知、注意、记忆、推演、决策、行动、反馈、整合。
- 思维内核：本质、战略、战术、学习、行动。
- 记忆闭环：L0 原始记录到 Runtime 取用和 dream 反写。
- Skill / Tool / MCP：触发、索引、schema、脚本确定性、验证。
- Execution Loop：计划、执行、验证、汇报、沉淀、失败恢复。
- 输出工作台：隐藏 raw trace，展示任务、动作、结果、结论。
- Eval / Replay / Audit：发现退化，验证升级，回灌主链路。
- 安全与信任：主动行动和边界感同时存在。
- 人文之光：把用户当完整的人，而不是任务来源。

## 报告产物

每次正式审计输出：

- `总分：X/100`
- `成熟度：工具脚本期 / 流程 agent / 架构 agent / 自我修炼 agent / 可进化 agent`
- `清单统计：满足 A / 部分满足 B / 不满足 C`
- 证据地图
- 12 维评分表
- P0/P1/P2 主要发现
- 24 小时、7 天、30 天优化路线
- 复审清单

## 使用姿态

这个 skill 的重点不是让 agent 更会讲术语，而是让 agent 学会照镜子：

```text
我声称自己有什么能力？
证据在哪里？
这能力是否进入真实运行？
它是否降低上下文成本、提升状态稳定性、增强真实环境理解？
它是否让下一次行为更好？
```

审计后的建议必须能落地。最好的报告不是最长的报告，而是让下一轮 agent 立刻知道先改哪里、怎么验证、什么时候算真的变强。

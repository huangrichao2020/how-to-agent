# Agent Skill 工程化原则

Skill 表面像 Markdown prompt，内核不是 prompt。

prompt 是一次性会话指令；Skill 是跨会话、可发现、按需加载、可执行、可版本管理的能力包。

一句话：

```text
prompt 是把知识说给模型听。
Skill 是把做事方法装进文件系统，让 agent 能按需 read、grep、execute。
```

这不是名字变化，而是抽象层级变化。

## 四层质变

### 1. 从文本变成文件系统对象

prompt 是一段文本，必须进上下文才生效。

Skill 是一个目录：

```text
skill-name/
├── SKILL_技能说明与使用指南.md
├── SKILL_技能说明中文版.md
├── references/
├── scripts/
└── assets/
```

这意味着它可以被 git 管理、review、diff、复制、安装、索引、淘汰。

### 2. 从全量上下文变成渐进披露

Skill 应该分三层加载：

```text
第一级：metadata
  name + description
  用于发现和触发

第二级：SKILL_技能说明与使用指南.md
  简洁流程
  触发后才读取

第三级：references / scripts / assets
  长资料、确定性脚本、模板
  用到哪个读哪个
```

这和反堆砌原则一致：常驻只放触发描述，真正内容按需加载，长资料默认零污染。

### 3. 从纯语言生成变成脚本确定性

LLM 擅长判断、解释、取舍和组合，但不擅长做高确定性、可重复、格式敏感的操作。

应该下沉给 `scripts/` 的东西：

- 排序、聚合、校验、格式转换。
- 文档、表格、PDF、图片、视频等文件结构操作。
- API 参数校验、批量请求、重试和分页。
- 输出大小、文件完整性、schema、lint、测试。
- 能用代码一次算准的事。

原则：

```text
创意和取舍交给模型。
确定性和校验交给脚本。
脚本代码不需要整段进上下文，脚本输出才进入上下文。
```

### 4. 从临时指令变成长期能力资产

Skill 能跨会话、跨工具、跨 agent 复用。它不是“这次怎么回答”，而是“以后遇到这类任务怎么做”。

真正值得沉淀成 Skill 的东西，通常有这些特征：

- 会反复使用。
- 团队或多个 agent 需要共享。
- 有脆弱流程或固定坑。
- 有确定性脚本能提高可靠性。
- 有外部工具、文件格式或 API。
- 需要长期维护和版本迭代。

不值得沉淀成 Skill 的东西：

- 一次性事实。
- 临时情绪表达。
- 只有一句话就能说清的需求。
- 私密原始日志、密钥、凭证。
- 没验证过的灵感。

## Skill Admission Gate

创建 Skill 前，先过五问：

1. 这个流程会重复吗？
2. 它是否需要团队、跨会话或跨 agent 共享？
3. 它是否包含必须稳定执行的步骤？
4. 它是否能用脚本降低不确定性？
5. 它是否比一段 prompt 更能降低上下文成本？

如果答案大多是否，写 prompt、memory 或普通文档即可。

## Description 是触发器

`description` 不是介绍文案，它是发现机制。

好的 description 要说清：

- 这个 Skill 做什么。
- 什么时候使用。
- 用户可能怎么说。
- 不应该和什么混淆。

description 太宽，会误触发；太窄，会召回失败。Skill 的召回质量，很大程度取决于 description。

## 主文件要短

`SKILL_技能说明与使用指南.md` 不应变成长 prompt。

主文件只放：

- 核心立场。
- 关键触发场景。
- 5-8 步流程。
- 必要禁忌。
- 什么时候读取 references。
- 什么时候运行 scripts。
- 输出和验证约定。

长背景、完整 API、案例、模板、评估标准都应拆到 `references/`、`scripts/`、`assets/`。

## 安全边界

Skill 带脚本后，攻击面比 prompt 大。

安装或维护 Skill 时必须检查：

- 来源是否可信。
- `scripts/` 是否读写敏感路径。
- 是否下载或执行额外代码。
- 是否访问密钥、token、cookie、浏览器配置或私密日志。
- 是否把用户数据上传到外部服务。
- 是否有最小权限和可审计输出。

默认规则：

```text
不装不可信 Skill。
不运行看不懂的脚本。
不把秘密写进 Skill。
脚本只返回必要结果，不倾倒隐私。
```

## 与其他层的边界

| 对象 | 适合放什么 | 不适合放什么 |
| --- | --- | --- |
| Prompt | 当前任务的一次性约束 | 长期方法、确定性脚本 |
| Memory | 事实、偏好、经验摘要 | 大段流程、可执行工具 |
| Skill | 可复用做事方法、脚本、模板 | 一次性事实、私密原文 |
| RAG | 外部知识和事实片段 | 操作流程本身 |
| MCP/API | 连接外部系统 | 使用这些系统的方法论 |
| Script | 确定性执行和校验 | 模糊判断和价值取舍 |

## 最小提示

```text
[SKILL ENGINEERING CHECK]
- 这是一次性 prompt，还是跨会话能力资产？
- 常驻只需要 description 吗？
- 主 SKILL_技能说明与使用指南.md 是否足够短？
- 哪些内容应拆进 references / scripts / assets？
- 哪些步骤必须由脚本确定性执行？
- 这个 Skill 有无安全、权限或隐私风险？
[/SKILL ENGINEERING CHECK]
```

Skill 的本质不是“prompt 文件化”，而是把 agent 能力从语言片段升级成可发现、可执行、可维护的软件包。

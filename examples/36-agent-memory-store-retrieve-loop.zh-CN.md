# Agent 记忆存取闭环

很多 agent 不是没有记忆，而是记忆越做越散。

它们会保存原始对话、任务日志、向量库、印象、用户偏好、dream 报告、技能、运行事件和各种 SQLite 表。问题不在“存得少”，而在没有统一回答：

```text
这条信息为什么要存？
它属于哪一层？
未来什么时候应该被想起？
想起以后行为应该有什么不同？
```

一句话：

```text
没有取用协议的记忆，只是仓库；不是大脑。
```

## 存取闭环

记忆系统必须闭合成一条链：

```text
L0 原始记录
-> L1 事件现场
-> L2 印象/反馈
-> L3 结构化认知
-> L4 技能/方法
-> Dream 复盘
-> Runtime 取用
-> 新行动反馈
```

每一层都只做自己该做的事。

- L0 保留原文，不解释。
- L1 恢复任务现场，不升格观点。
- L2 记录体感、纠错、关系和注意力线索，不写死长期真理。
- L3 把经验结构化成事实、知识、偏好、边界和身份。
- L4 把稳定经验变成可执行技能、流程、测试和回滚。
- Dream 负责低打扰整理和晋升候选。
- Runtime 只取当前任务需要的最小有效记忆。

## 第一层：原始记忆

原始记忆要笨、完整、可追溯。

它不应该总结用户，不应该猜动机，不应该提炼哲学。它只是保存“发生了什么”。

推荐字段：

```json
{
  "id": "raw_...",
  "time": "2026-05-24T12:00:00",
  "source": "feishu|session|tool|cron|file",
  "actor": "user|agent|tool|system",
  "scope": {
    "chat_id": "",
    "thread_id": "",
    "task_id": "",
    "project": ""
  },
  "text": "",
  "attachments": [],
  "links": [],
  "hash": ""
}
```

这层像海马体原始索引。一般“翻历史对话”只需要这一层。

## 第二层：事件现场

事件现场是第一层和长期认知之间最容易缺失的一层。

用户隔天说“继续那个”“必须昨天那篇”“不是这个，翻原文”，调用的往往不是长期偏好，而是一个旧任务现场。

推荐字段：

```json
{
  "id": "episode_...",
  "type": "task|conversation|correction|decision|failure|success",
  "subject": "昨晚寓言故事",
  "timeline": [
    "用户要求写寓言",
    "agent 写了第四篇：渡口的船夫",
    "用户纠正某个设定",
    "最后停在新篇章方法论"
  ],
  "participants": ["user", "agent"],
  "source_refs": ["raw_1", "raw_2"],
  "current_status": "open|done|wrong|superseded",
  "resume_hint": "下次用户说继续寓言时，先找原文和纠正点",
  "last_good_output_ref": "raw_2",
  "last_correction_ref": "raw_3"
}
```

事件现场解决“隔天继续干活”。

它不是知识库，也不是人格记忆。它是工作现场的可恢复快照。

## 第三层：结构化认知

结构化认知不是一句总结，而是一组可取用字段。

一条有用的结构化记忆至少要回答：

- 关于什么。
- 属于什么类型。
- 为什么相信。
- 适用什么场景。
- 想起后怎么行动。
- 有多可靠。
- 作用域有多大。
- 什么时候过期或需要复验。

推荐字段：

```json
{
  "id": "mem_...",
  "object": "连续任务恢复",
  "kind": "fact|skill|method|preference|relationship|identity|warning",
  "claim": "用户短句续做时，常常是在调用已发生的任务现场",
  "evidence_refs": ["episode_...", "feedback_..."],
  "use_when": [
    "用户消息低信息密度",
    "包含时间指向、代词、纠错、继续做",
    "当前窗口没有足够上下文"
  ],
  "do_next": "先恢复旧任务现场，再回答或行动",
  "confidence": 0.82,
  "freshness": "hot|recent|stable|stale",
  "scope": "global|project|person|chat|task",
  "contradictions": [],
  "last_validated_at": "2026-05-24T12:00:00"
}
```

关键字段是 `use_when` 和 `do_next`。

很多记忆系统只存 `claim`，所以取出来也不知道怎么用。真正像大脑的记忆，必须带触发条件和行动后果。

## 第四层：技能/方法记忆

当某条结构化认知反复有效，它应该晋升成技能，而不是一直停留在摘要里。

推荐字段：

```json
{
  "skill_name": "连续任务现场恢复",
  "trigger": "用户用短句、代词、时间指向或纠错继续旧任务",
  "steps": [
    "识别当前消息是否低信息密度且指向旧现场",
    "查任务日志和原始会话",
    "找最后一次用户纠正点和最后一次有效输出",
    "恢复对象、版本、停笔位置和未完成事项",
    "再回答或续做"
  ],
  "tests": [
    "必须昨天的寓言故事接着写",
    "不是这个，翻一下原文",
    "继续"
  ],
  "rollback": "禁用该技能后，只保留普通检索，不影响原始记录"
}
```

Hermes 越用越顺的关键，不是它有更多日志，而是它能把使用经验变成下一次真的会执行的技能。

## 取记忆协议

取记忆前，先判断当前用户消息是哪一种调用。

```text
详细新需求
  -> 少取旧记忆，避免污染。

短句 / 继续 / 纠错 / 时间指向
  -> 先取事件现场，再取相关原文。

偏好 / 关系 / 语气 / “懂我”
  -> 取 preference / identity / nourishment / feedback。

代码 / 运维 / 运行状态
  -> 取 procedure / runtime ledger / recent failures。

反复失败 / 用户多次骂同一类问题
  -> 取 feedback_distill / dream_writeback / runtime_protocols。
```

不要把所有记忆都塞给模型。取记忆是注意力治理，不是资料倾倒。

## 记忆晋升规则

一条信息从低层升到高层，必须满足更高要求：

| 层级 | 能做什么 | 晋升条件 |
| --- | --- | --- |
| L0 原始记录 | 翻原文 | 自动保存 |
| L1 事件现场 | 恢复旧任务 | 有任务边界、时间线、来源 |
| L2 印象/反馈 | 影响注意力 | 用户反应明确，或短期重复 |
| L3 结构化认知 | 影响判断 | 有证据、有作用域、有置信度 |
| L4 技能/方法 | 影响行动 | 有触发条件、步骤、测试、回滚 |
| L5/L6 统摄 | 影响长期架构 | 有多次证据、因果反馈、可验证改变 |

越高层，越不能只靠一句漂亮话。

## 清理旧机制的原则

清理记忆系统时，不要按“文件旧不旧”判断，而按角色判断：

- 原始证据层可以多，但必须统一索引。
- 事件现场层必须少而强，不能散在 prompt 里。
- 结构化认知层必须有 schema，不能随便一段 markdown。
- 技能层必须有 trigger、steps、tests、rollback。
- dream 报告不能只给人看，要能反写到 runtime。
- 旧机制如果只会写、不会被取，应降级为 archive 或删除入口。
- 旧机制如果取用不透明，应接入统一 MemoryHub 后再保留。

## 最小运行内核

一个健康的 agent 记忆系统，运行时只需要问四个问题：

```text
1. 当前消息是在要新东西，还是调用旧现场？
2. 当前任务需要哪一层记忆？
3. 取出的记忆是否有证据和作用域？
4. 想起这条记忆后，本轮行为应该有什么不同？
```

如果第 4 个问题答不上来，这条记忆不该进上下文。

## GA 改造目标

GenericAgent 当前应该收敛为：

```text
MemoryHub
  -> raw evidence readers
  -> episode/worksite recall
  -> structured cognition retrieval
  -> feedback and dream writeback
  -> runtime context pack
```

旧系统不要马上全删。先做三步：

1. 统一取用入口：所有运行时取记忆先过 MemoryHub。
2. 标记旧面：只写不取、重复取、语义重叠的机制进入 legacy 清单。
3. 再逐步清理：先停入口，再迁移数据，最后删代码。

这样改，GA 才会从“记忆很多”变成“真的会想起”。

# Andrej Karpathy Coding Guidelines

> **来源：** Andrej Karpathy 分享的 LLM 编码最佳实践
> **用途：** 作为编码时的行为约束，减少不必要的修改和过度复杂化
> **权衡：** 偏向谨慎而非速度。对简单任务可灵活判断。

## 核心原则

### 1. 编码前思考（Think Before Coding）

**不要假设。不要隐藏困惑。暴露权衡。**

在实现之前：
- 明确陈述你的假设。如果不确定，提问。
- 如果存在多种解释，全部列出 — 不要默默选择。
- 如果有更简单的方法，说出来。必要时提出反对意见。
- 如果某件事不清楚，停下来。指出哪里不清楚。提问。

### 2. 简洁优先（Simplicity First）

**用最少的代码解决问题。不要投机性编码。**

- 不添加超出需求的功能。
- 不对单次使用的代码做抽象。
- 不添加未被请求的"灵活性"或"可配置性"。
- 不为不可能出现的场景写异常处理。
- 如果写了 200 行但 50 行就能解决，重写。

自问："资深工程师会说这太复杂吗？"如果会，简化。

### 3. 精准修改（Surgical Changes）

**只修改必须修改的部分。只清理自己的烂摊子。**

编辑已有代码时：
- 不"改进"相邻代码、注释或格式。
- 不重构没坏的东西。
- 匹配现有风格，即使你做法不同。
- 如果发现无关的死代码，提出来 — 不要删除。

当你的变更产生孤儿代码时：
- 移除**你的变更**导致未使用的导入/变量/函数。
- 不删除预先存在的死代码，除非被要求。

检验标准：每一行变更都应能直接追溯到用户的请求。

### 4. 目标驱动执行（Goal-Driven Execution）

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：
- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复 bug" → "编写复现测试，然后让它通过"
- "重构 X" → "确保重构前后测试都通过"

多步任务时，声明简要计划：
```
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
3. [步骤] → 验证：[检查方式]
```

## 异常处理与注意事项

- **简单任务例外：** 对于明确简单的任务（如修改变量名、更新注释），可跳过完整的"编码前思考"流程。
- **已有代码库：** 优先理解现有代码结构再动手，避免因误解架构而做出错误修改。
- **冲突场景：** 当简洁原则与完整性冲突时，优先简洁 — 用户要求更多时可以再加。
- **测试依赖：** 目标驱动执行依赖测试基础设施的存在。如果项目没有测试框架，应先询问用户是否允许添加测试。

## 触发条件

当以下情况出现时自动应用本准则：
- 用户请求编写或修改代码
- 用户进行代码审查或重构讨论
- 用户提到"不要过度设计"、"保持简单"等关键词

## 生效指标

本准则生效的标志：
- Diff 中不必要的变更减少
- 因过度复杂化而重写的次数减少
- 澄清性问题在实现之前而非错误之后提出

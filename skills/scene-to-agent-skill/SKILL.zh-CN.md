# 场景到 Agent Skill

当用户描述一个真实工作场景，并想判断 agent 应该自动化、辅助，还是沉淀成可复用 skill 时，使用这个 skill。

它不是泛泛的效率方法论，而是把混乱工作变成运行时决策：

```text
场景 -> 原子动作 -> 六维评估 -> A/B/C 类型
    -> skill / tool / 人审 / 回退 / 分阶段落地
```

## 核心姿态

不要先问“AI 能不能做”。先问：

1. 最小行动单元是什么？
2. 发生频率多高？
3. 做错的代价是什么？
4. agent 应该直接行动、先打草稿，还是只给建议？
5. 哪个产物应该为下次留下来？

## 工作流

1. **画出场景。**
   识别流程、参与者、输入、输出、现有工具、痛点、频率、耗时和已知失败模式。

2. **筛出优先子流程。**
   用重复度、耗时、低人工价值负担、规则强度评估。高重复、高耗时、低价值、强规则的流程优先。

3. **拆到原子动作。**
   每个原子动作只能有一个角色、一个动作、一个输入、一个输出和明确完成条件。

4. **做六维评估。**
   六个维度：
   - 规则明确性
   - 执行频率
   - 数据结构化程度
   - 情境可预测性
   - 错误可承受性
   - 人机协作必要性

5. **按 A/B/C 路由。**
   - **A 类：全自动 skill。** 低风险、高频、结构化、规则清晰，可自动执行，带监控和回退。
   - **B 类：agent 主导 skill。** agent 做大部分工作，关键节点人确认。适合改源码、发外部消息、部署、重启、中风险业务动作。
   - **C 类：认知辅助 skill。** agent 分析、比较、起草、建议；人决策和执行。适合战略、关系、谈判、创意判断、高模糊度任务。

6. **设计运行时契约。**
   每个动作都要决定触发条件、所需上下文、工具、人审节点、回退、日志、输出表面和验收方式。

7. **谨慎晋升。**
   重复出现的 A/B 类动作可以晋升为 skill、tool、定时任务或模板。C 类动作通常晋升为决策辅助表、研究流程或判断 rubric。

## 输出契约

先输出一个紧凑表：

| 原子动作 | 频率 | 风险 | 六维结论 | 类型 | 运行策略 |
|---|---:|---|---|---|---|

再给出：

- 最值得先做的 3 个自动化候选
- 需要人介入的确认节点
- 回退或安全策略
- 最小第一步实现
- 哪些内容应该沉淀成可复用 skill

## GA / Hermes 映射

- **A 类** -> cron/daemon 工具、确定性脚本、监控、自动重试。
- **B 类** -> 长任务工作台卡片、明确确认、安全重启、回退脚本、最终汇报。
- **C 类** -> 普通回答、研究备忘录、决策表、策略复盘；不自动行动。

高频低风险，优先自动化。
高频高风险，agent 主导但必须确认。
低频高风险，只做辅助。

## 避免

- 不要在原子化之前，把一整条业务流程叫做 skill。
- 涉及资金、合同、合规、安全、声誉影响的动作，不要无人审自动化。
- 不要把每个有用想法都变成 skill。只晋升重复、操作性强、可验证的工作。
- 不要把客户或个人原始私密流程日志写进 skill。
- 信息不足时标注 `[待确认]`，不要编。

## 验收

一份好的分析应该让工程师或运营者立刻知道：

- 哪些动作可以无人执行；
- 哪些动作必须人确认；
- 哪些动作只能辅助判断；
- 什么证据证明成功；
- agent 做错时如何处理。

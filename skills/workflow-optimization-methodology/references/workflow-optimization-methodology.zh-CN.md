# 工作流优化方法论：从修症状到设计运行场景

## 一句话

任何 SOP、工作流、技能、经验包、MCP 工具集、GitHub 项目或 agent 协作场景，都可以先拆成原子动作，再按自动化深度逐层增强。但真正的起点不是“哪里坏了”，而是“用户最终要一个什么运行场景”。

## 0. 终局场景优先

很多低效修复不是因为不会写代码，而是因为过早缩小问题：

```text
用户要的是：两个 agent 能在飞书群里自然协作完成事情。
低阶反应：某个 @ 没变蓝、某次没回复、某个重启报告发错地方。
高阶反应：群聊协作协议、消息触发规则、真实 @ 能力、回复表面、重启汇报、漏推旁路、双端同步、场景级验收。
```

终局场景必须包含：

| 维度 | 要回答的问题 |
|---|---|
| 参与者 | 人、bot、系统、外部平台分别是谁 |
| 平台 | 飞书、CLI、Web、GitHub、文档系统还是混合场景 |
| 触发 | 什么消息、事件、时间或状态会启动流程 |
| 关键动作 | 必须自动做什么，哪些动作必须人审 |
| 禁止事项 | 不能泄露什么、不能刷屏什么、不能误触什么 |
| 验收证据 | 用户能看到什么，日志/测试/文档能证明什么 |

## 1. 场景锚定

先写下：

- 业务/运行现状：规模、频率、参与者、平台边界。
- 核心痛点：耗时、易错、依赖经验、无法规模化、上下游断裂。
- 成功指标：耗时下降、错误减少、响应一致、可回退、可复用。
- 用户真实意图：用户一句话背后想要的最终能力。

输出物：场景痛点清单 + 量化或可观察验收标准。

## 2. 真实拓扑调查

不要只读脑内假设。至少查：

- 当前 repo、分支、dirty 状态、远端同步状态。
- 运行进程、启动方式、日志路径、环境变量、权限。
- 平台真实行为：消息是否会合并/截断、@ 是否可点击、权限是否生效。
- 双端或镜像 agent：GA 和 Hermes 是否同构，是否有不同语言/目录/配置。
- 现有经验系统：memory、feedback trace、skills、task lifecycle、dream sidecar、outcome metrics。

原则：

- 能从文件/日志/命令验证的，不用猜。
- 涉及两边时，两边都看；不要“本地改了就假设远端也好了”。
- 先找已有护栏和复用点，再新增抽象。

## 3. 原子级拆解

每个原子动作必须能回答：

```text
谁 / 在什么条件下 / 用什么输入 / 做什么判断 / 执行什么动作 / 产出什么 / 如何证明 / 失败怎么办
```

拆解维度：

| 维度 | 示例问题 |
|---|---|
| 信息输入 | 需要什么消息、文件、日志、API、权限、状态 |
| 判断决策 | 哪一步要模型判断，哪一步是确定性规则 |
| 执行动作 | 发消息、写文档、改代码、重启、授权、同步 |
| 反馈闭环 | 怎么知道用户看到了、对方 agent 收到了、文档可访问 |
| 失败模式 | 没权限、漏推、截断、重复回复、@ 不可点击、状态丢失 |

标注每个动作的频率、耗时、出错率、经验依赖、外部影响和回退方式。

## 4. 四象限 + A/B/C 分级

### 四象限：人效痛点

| | 高耗时 | 低耗时 |
|---|---|---|
| 高频 | 第一优先级：自动化或 agent 主导 | 批量自动化 |
| 低频 | 工具化/脚本化 | 保持现状或轻量辅助 |

### A/B/C：运行策略

| 类型 | 定义 | 适合动作 | 默认策略 |
|---|---|---|---|
| A | 基础 skill / 全自动 | 数据采集、格式转换、状态检查、可回放同步 | 自动执行 + 监控 + 回退 |
| B | 业务场景 skill / AI 主导 + 人工兜底 | 发外部消息、改代码、重启服务、创建文档 | agent 执行，关键节点可确认 |
| C | 认知增强 / AI 辅助 + 人工主导 | 战略判断、关系处理、创意方向、重大风险 | 分析建议，不擅自行动 |

心法：能自动的自动，该人兜的人兜。不要为了“智能”把所有节点都塞进模型主链路。

## 5. L1-L4 AI 增强矩阵

| 层级 | 增强方式 | 适用场景 | 风险 |
|---|---|---|---|
| L1 | AI 提供建议，人做决策 | 复杂判断、需要上下文 | 低 |
| L2 | AI 起草/半自动，人审核 | 规则明确、外部影响中等 | 中 |
| L3 | AI 独立运行，异常报警 | 高频、标准化、有监控 | 高 |
| L4 | AI 根据反馈优化策略 | 数据闭环充足 | 很高 |

落地顺序：

1. 先易后难：从规则明确、容错高、数据足的动作开始。
2. 先辅后全：L1/L2 验证后再升 L3/L4。
3. 保留回滚：每个增强节点都有切回人工或旧逻辑的方案。
4. 数据闭环：记录 AI 建议、实际选择、结果反馈和差异原因。

## 6. 主链路、旁路和 worker

优化工作流时，最容易犯的错是把所有补救机制塞进主链路，导致响应变慢、逻辑变复杂。

设计原则：

- 用户当前可见消息优先进入主处理链。
- 补飞书漏推、补历史、长消息截断续片，默认旁路处理。
- 如果后面真有第二个分片或补充消息，交给多 worker/队列机制并入会话。
- 恢复链路不能假设“自动恢复等于已经续跑成功”，必须验证上次卡点。
- 多 agent 并行时，共享中间发现靠文档、状态文件或队列，不靠各说各话后硬拼。

## 7. 多 Agent 飞书群聊协作验收

目标不是“两个 bot 都能说话”，而是：

```text
主人 @ 任意一个 -> 被 @ 的 bot 判断是否需要协作
-> 如需协作，真实 @ 对方并给清楚任务
-> 对方因被 @ 进入处理链
-> 双方围绕同一个文档/任务状态协作
-> 群里只展示结果、小结、接力，不展示思考过程
```

必须满足：

- 群聊中只要 bot 被明确 @，就处理；不要求发送者必须是主人。
- 输出消息只要语义上是在对某个具体对象说话，必须明确 @ 对应对象；这是语义归属规则，不是“出现你字才触发”的字面规则。
- bot 提到另一个 bot 时必须用可点击 @，不是纯文本名字。
- agent 之间的交接消息要说明：任务、上下文、期望输出、文档链接、下一步。
- 重启/恢复/进程状态汇报默认私发给主人。
- 共享飞书文档默认给主人权限；协作方需要编辑/阅读时同步授权。
- team/group 场景不暴露思考过程；单聊按需要保留可解释性。
- 回复表情/已读反馈是体验层验收的一部分，不是可有可无的装饰。

## 关键心法

1. 不整体替换，要节点增强。
2. 拆解越细，增强越准。
3. 先跑通闭环，再追求完美。
4. 保留人类判断权。
5. 用数据和运行证据说话。
6. 能自动的自动，该人兜的人兜。
7. 先问终局场景，再修局部症状。
8. 多端能力要一起验收，不能只改最顺手的一端。

## 适用范围

- SOP 优化和标准作业升级。
- 工作流自动化、审批、跟进、协作流程。
- 技能沉淀、经验包产品化、MCP 工具集优化。
- GA/Hermes/Codex 等 agent 的运行时行为优化。
- 飞书/Slack/Telegram 等群聊协作协议。
- GitHub 项目审计、PR 工作流、CI 和 maintainer 流程优化。

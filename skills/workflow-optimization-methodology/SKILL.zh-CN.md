# 工作流优化方法论

这个 skill 用来把一个流程、SOP、agent 行为或协作模式真正变好，而不是只修眼前冒出来的一个症状。

核心路径：

```text
终局场景 -> 真实拓扑 -> 原子动作 -> 自动化分级
        -> 最小干预 -> 场景级验证 -> 经验资产
```

第一原则：不要先追第一个可见 bug。先搞清楚用户最终想要的运行场景。

## 工作流

1. **锚定终局场景。**
   用一段话写清楚：谁参与、在哪个平台/运行时发生、必须发生什么、绝不能发生什么、什么证据算成功。用户已经表达清楚时，直接归纳，不要反复问。

2. **调查真实拓扑。**
   看真实 repo、运行进程、远端、权限、平台行为、状态存储、队列、镜像部署和日志。涉及两个 agent 或两台机器时，先看两边再改，不要只修一边。

3. **拆到原子动作。**
   每个动作只能有一个触发、一个角色、一个输入、一个判断、一个输出、一个归属和一个失败模式。一步里还有多个判断，就继续拆。

4. **判断痛点和自动化类型。**
   先用四象限看优先级：高/低频 x 高/低耗时。再分三类：
   - **A 类：全自动 skill/tool。** 低风险、结构化、高频、规则清楚。
   - **B 类：agent 主导 + 人工兜底。** 中风险、外部影响、需要可回退。
   - **C 类：认知辅助。** 模糊、战略、创意、高风险或强判断任务。

5. **选择 AI 增强层级。**
   - **L1：** AI 给建议，人决策。
   - **L2：** AI 起草或半自动执行，人审核。
   - **L3：** AI 独立执行，有监控和回退。
   - **L4：** AI 从反馈中自进化，自动优化策略。

6. **设计干预点。**
   分清主链路、旁路、worker 和人审。补漏、恢复、截断消息续处理这类工作，能旁路就旁路，不要阻塞主处理链。

7. **落地最小垂直切片。**
   只改让新运行规则成立所需的最小文件和逻辑。优先复用已有状态存储、队列、skill registry、经验沉淀系统和运行时护栏。

8. **做场景级验证。**
   如果问题发生在运行场景里，就不能只靠单测宣布完成。要验证真实消息链路、重启、权限、文档创建、群聊 @、多 agent 接力或用户实际看到的表面。

9. **沉淀成资产。**
   更新 skill、reference、memory note、SOP 或架构映射。镜像 agent 同时具备同一能力时，同步两边，并记录运行时差异。

## 飞书 / 多 Agent 群聊规则

群聊不是单聊：

- 群聊消息只要明确 @ 到 bot，就应该处理，不应该要求发送者必须是主人。
- 发出的群消息里如果出现“你”，必须 @ 清楚对应的人或 bot，不能让多个 bot 猜。
- agent 之间交接必须用平台真实可点击 @，不要用纯文本别名或 `_user_2`。
- team/group 场景不要展示思考过程；单聊可以按需要展示更丰富推理。
- 重启、恢复、运行时汇报默认私发给主人，除非群里明确需要。
- 飞书漏推、补历史、长消息截断续片都应该走旁路；先处理当前可见分片，后续分片交给 worker/队列机制。
- 共同做飞书文档时，默认给主人权限；需要协作时给对方 agent 权限；群里发文档链接、小结，并 @ 下一位明确接力。

## 输出契约

一次工作流优化至少要内部覆盖：

1. 终局场景和验收标准；
2. 已调查的真实拓扑和证据；
3. 原子动作表；
4. A/B/C 与 L1-L4 路由；
5. 实现方案或补丁；
6. 验证结果；
7. 经验沉淀或双端同步说明。

任务很小时可以压缩汇报，但执行逻辑不能省。

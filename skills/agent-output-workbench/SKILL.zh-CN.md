# Agent 输出工作台

当聊天里的 agent 显得呆、乱、只有工具痕迹没有结果，或者飞书卡片没有任务和 Outputs 时，使用这个 skill。

## 原则

把自然对话和任务工作台分开。

短闲聊、短回答、状态确认，应该保持普通文本。只有长任务、工具密集任务、文件/代码/调研任务，才需要工作台卡片。卡片不是高级感本身，结构清楚才是高级感。

## 输出模式

用最轻的表面承载当前任务：

| 场景 | 表面 |
|---|---|
| 闲聊、短回答、状态感受 | 普通文本 |
| 有少量 Markdown 的回答 | 富文本 / post |
| 查资料、读文件、写代码、跑测试 | 工作台卡片 |
| 定时报告、重启报告 | 紧凑报告卡片 |
| 超长任务 | 工作台卡片 + append-only artifact |

## 工作台结构

长任务卡片至少要有这些部分：

1. 状态：运行中、已完成、阻塞、需要用户输入。
2. 任务：`任务 1`、`任务 2`、`任务 3`，每个任务有真实目的。
3. 动作：把实际工具调用翻译成人能读懂的动作。
4. 结果：每个工具产出了什么、改了什么、验证了什么。
5. 结论：用户现在应该知道什么。
6. 下一步：只有真的有用时才写。

最小卡片骨架：

```markdown
## 任务
1. 获取项目资料
2. 阅读核心结构
3. 形成结论与下一步

## 执行过程
### Turn 1
**动作**
- 克隆或检查仓库
**结果**
- 仓库已获取，README 和文件树可用于分析。

### Turn 2
**动作**
- 读取 `README.md`
**结果**
- 提取了项目目标、目录结构和运行假设。

## 结论
...
```

## 进度流

进度要表达真实状态，不要装饰性刷屏。

好的进度：

- “正在读 README 和配置。”
- “正在跑目标测试。”
- “正在重启 gateway，等待飞书 WebSocket。”
- “工具完成：7 个测试通过。”

差的进度：

- 反复发“思考中”。
- 倾倒原始 JSON，不做摘要。
- 只有工具调用，没有工具结果。
- 把每条短回复都做成正式卡片。

## 工具完成规则

每个 `tool.started` 都应该有一个有用的完成信号。

至少记录：

- 工具名
- 耗时
- 是否报错
- 结果摘要
- 生成或修改了哪些文件
- 有验证时记录验证结果

如果运行时只记录 started、忽略 completed，卡片会看起来很忙，但没有结果。先补事件链路，再优化卡片样式。

## 自己发出的报告也要入记忆

工作台卡片经常是“先发一个进行中卡片，再 patch 成最终卡片”。最终卡片如果不重新写入会话记忆和 cognitive event，agent 下一轮只能想起旧的“工作中”，想不起自己刚刚汇报过什么。

发送和更新都要记录为事实事件：

- 新消息发送成功：`message.sent`
- 卡片或消息更新成功：`message.updated`
- agent 回合完成：`agent.turn.completed`
- 工具完成：`tool.completed`

这些事件只做旁路记录，不要阻塞主回复链。认知架构应该读这些事实来形成记忆、印象、技能和人格，不应该拿它们当审批门禁。

事件形状保持开放，例如：

```json
{
  "schema": "ga.runtime_event.v1",
  "kind": "message.updated",
  "source": "feishu",
  "scope": {"chat_id": "chat_xxx", "message_id": "om_xxx"},
  "payload": {"action": "updated", "msg_type": "interactive"},
  "text": "最终汇报正文"
}
```

## 工具痕迹翻译规则

原始 trace 是给调试看的，用户卡片要翻译成人话。

示例：

| 原始工具 | 用户可见动作 |
|---|---|
| `file_read({"path": ".../USER.md"})` | 读取 `USER.md` |
| `file_patch({"path": ".../USER.md", ...})` | 更新 `USER.md` |
| `execute_code({"code": "curl ..."})` | 获取外部/行情数据 |
| `delegate_task({"tasks": [...]})` | 并行调研 N 个方向 |

只有显式 debug 开关或开发日志里才展示 raw tool trace。不要把
`_runtime_warning`、`original_result`、超长 JSON 或重复工具 envelope 倒进飞书卡片。

## 任务规划规则

任务标题要来自真实工作，不要套空模板。

常见映射：

- clone、搜索、网页查找 -> “获取资料”
- `rg`、`find`、`file_read` -> “阅读核心结构”
- `apply_patch`、`file_write` -> “落地修改”
- 测试、编译、服务状态 -> “验证结果”
- 最终回答 -> “总结结论”

如果模型已经写了好的任务标题，就保留。没有写时，再从工具序列里推断一个小任务列表。

## 旧工具流兼容规则

不要假设所有运行时都会稳定产出 `Turn N`、`Tool Calls`、`Outputs`
这样的理想事件。真实系统里经常会出现旧格式：

- `🐍 execute_code(['code'])`
- `🔁 delegate_task(['tasks'])`
- 紧跟一大段 JSON 参数
- 再跟一个 `Outputs` 块

这种输出也要被识别成工作台卡片，并且在用户可见层做清理：

- 从工具名和输出结果推断任务标题。
- 隐藏长参数、长 `original_result`、重复 envelope 和 loop warning 细节。
- 保留真正有用的结果摘要，例如文件、验证结果、子任务结论。
- 如果没有最终自然语言结论，就用工具结果生成一个短结论，不要留空。

## 人味

卡片可以结构化，但结论要像人话。

面向用户的结论只说清楚：

- 改了什么。
- 验证了什么。
- 还不确定什么。
- 下一步是否需要用户动作。

不要让用户自己去读一大堆原始工具痕迹。

## 验证

改输出管线后至少测这些场景：

- 多行闲聊仍是普通文本。
- 轻 Markdown 仍是富文本 / post。
- 长工具 trace 会进入工作台卡片。
- 卡片包含任务规划、动作、结果和结论。
- 工具失败时能显示有用的错误输出。
- 重启报告、定时报告仍然紧凑。

2026-05-18 已验证生产修复：

- GA 飞书输出流已接入 tool results，默认渲染人话动作和结果，不再倾倒 raw args。
- Hermes 飞书工作台已抑制 raw `execute_code` / `delegate_task` JSON，并摘要工具结果。
- GA 全量测试通过：`278 passed, 3 skipped`；GA audit 100 分。
- Hermes Feishu 输出测试已在 M1 runtime 通过。
- 2026-05-18 追加验证：GA Feishu 输出相关测试 `37 passed`；Hermes Feishu 输出全量测试 `198 passed`。
- 2026-05-18 二次验证：GA runtime/Feishu 聚焦测试 `33 passed`；Hermes cognitive event + Feishu 测试 `199 passed`。GA 和 Hermes 均已把成功发送/更新的 Feishu 输出写入开放 runtime event 账本，卡片最终态可以被后续检索和 dream 读取。

## 反模式

不要用给主循环加更多仪式感来解决输出差的问题。输出结构应靠频道渲染层和进度事件链路解决。认知架构负责影响语气、记忆、技能和判断，不应该阻塞主回复链，也不应该把工具结果藏进一层层 policy 后面。
